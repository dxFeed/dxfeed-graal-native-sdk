◆ dxfg_v4_event_clazz_t

typedef dxfg_event_clazz_t dxfg_v4_event_clazz_t

The class of an event: tells which structure an event (dxfg_event_type_t) is.

In the Java implementation, all events are lined up in a hierarchy from the underlying EventType interface. In the C implementation, we specify the type in the event in a separate field because we cannot get it from the class name.

The comment of every value names the Java event class and its kind: a lasting event (LastingEvent: only the latest event of a symbol is kept), an indexed event (IndexedEvent: events of a symbol are told apart by an index and a source) or a time series event (TimeSeriesEvent: an indexed event with a time). The kind of the base class is inherited by its subclasses. The structure of a value is named by the value (DXFG_EVENT_QUOTE: dxfg_quote_t).

◆ dxfg_v4_event_type_t

typedef dxfg_event_type_t dxfg_v4_event_type_t

The base structure of every event: the first field of all the event structures.

clazz tells which event structure the pointer really points to (for example, DXFG_EVENT_QUOTE: dxfg_quote_t); cast the pointer to that structure to read the other fields.

Who creates and releases an event:

  • dxfg_EventType_new() creates an event that the caller owns; all its fields besides clazz and the symbol are zero (not NaN).
  • The SDK creates the events that it passes to a listener or returns as a result. An event passed to a listener belongs to the SDK: it is freed after the listener returns, copy what you need to keep. The events returned as a result belong to the caller.
  • An event of either origin, and a list of events, is released with dxfg_EventType_release() and dxfg_CList_EventType_release(): that frees the structure together with all its strings (the const char * fields, such as the event symbol).

◆ dxfg_v4_message_t

typedef dxfg_message_t dxfg_v4_message_t

The message event: a notification with an application-specific attachment.

It is neither a lasting nor an indexed event: messages are never conflated, its clazz is DXFG_EVENT_MESSAGE.

Javadoc

The attachment (the same for dxfg_configuration_t) is a UTF-8 null-terminated string (const char *, declared as void *) or NULL when there is no attachment:

  • Java -> C: a String attachment is passed as is, the other objects are passed as their string representation (toString()), no attachment is NULL. An attachment that Java cannot deserialize (e.g. its class is not registered for the native image) is NULL too, the SDK logs a warning then.
  • C -> Java: the attachment becomes a String, NULL is no attachment.

So a non-string attachment loses its type when it passes through C: if the event is published back (or forwarded to another endpoint), the Java receivers get the string instead of the original object.

The C API does not support arbitrary Java attachments: C can neither create nor read them. For a string payload prefer dxfg_text_message_t and dxfg_text_configuration_t (TextMessage, TextConfiguration): their text is a plain string that passes both ways without loss.

Memory:

  • The events that the SDK gives to the caller (to a listener, from dxfg_DXFeed_getLastEvent(), a promise, etc.) own their strings: the SDK frees them with the event (after the listener returns, or with dxfg_EventType_release() and dxfg_CList_EventType_release()). Copy the attachment to keep it longer.
  • The events that the caller allocates itself and passes to the SDK (dxfg_DXPublisher_publishEvents(), etc.) are only read: the SDK copies the attachment during the call, the caller allocates and frees it.
  • dxfg_EventType_release() of an event created by dxfg_EventType_new() frees its strings with the SDK's allocator. If the caller sets the attachment of such an event to its own string, it resets the attachment to NULL before the release and frees the string itself (the allocators of the caller and of the SDK may differ, e.g. on Windows).

◆ dxfg_v4_ObservableSubscriptionChangeListener_function_symbolsAdded

typedef dxfg_ObservableSubscriptionChangeListener_function_symbolsAdded dxfg_v4_ObservableSubscriptionChangeListener_function_symbolsAdded

The callback of a subscription change listener: symbols were added to the subscription.

It is called by the SDK after the symbols are added to the subscription of the Java side, on a Java thread (not necessarily the thread that registered the listener), while the SDK holds the lock of the subscription: the notifications of one subscription do not run at the same time. The symbols are decorated depending on the subscription: for a time series subscription they are dxfg_time_series_subscription_symbol_t.

The list belongs to the SDK and is freed after the function returns: do not release it, copy the symbols that you need to keep.

Parameters
[in]threadThe current GraalVM Isolate's thread.
[in]symbolsThe added symbols.
[in]user_dataThe user data passed to dxfg_ObservableSubscriptionChangeListener_new().
