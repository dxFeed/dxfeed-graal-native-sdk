# NetTestApi: the NetTest of the dxFeed Java API

`NetTestApi p` publishes generated Trade or TimeAndSale events through the `DXPublisher` of a dxFeed `DXEndpoint`;
`NetTestApi c` receives them through a `DXFeed` subscription and measures their end-to-end lag. It is the Java
counterpart of the C tool [NetTest](../../src/main/c/src/apps/NetTest/README.md) and takes the same command line, so
that the same publishing can be measured three ways with one mux, consumer and parsers: QD NetTest (records), this
tool (dxFeed events in Java) and the C tool (dxFeed events through the SDK). `NetTestApi c` is the consumer of the
benchmark.

It is a tool of QD's `Tools` (`NetTestApi`, next to `NetTest`), in the package `com.devexperts.qd.tools`, and
generates the symbols by the rules of QD NetTest's generator without changing QD. It is a separate Maven project, not
a module of the SDK build and not part of the SDK archives.

The NetTests of all language APIs follow one contract, the [NetTest specification](../../docs/wrapper-guide/nettest.md)
(`nettest/1`). Its table of the SDK tools shows the sections this tool follows, and
[Differences from the specification](#differences-from-the-specification) lists what it does not do yet. This README
describes the options the tool has.

## Getting the tool

It is deployed with every SDK release as `com.dxfeed:graal-native-sdk-nettest:<version>`, to the same repository as
the SDK archives: the jar of the tool and the all-in-one jar with QD (classifier `all`). Its QD version is the
`qd.version` of the SDK release. To build it from the sources (JDK 21 or later):

```shell
mvn -f tools/nettest/pom.xml package
```

The all-in-one jar is `tools/nettest/target/graal-native-sdk-nettest-0-SNAPSHOT-all.jar`. Run it with JDK 21 or later:

```shell
java -jar graal-native-sdk-nettest-<version>-all.jar NetTestApi p :6666 -S 50000 -r */1M -c stream --duration 7m
java -jar graal-native-sdk-nettest-<version>-all.jar NetTestApi c localhost:6666 -S 50000 -c stream --duration 7m --warmup 1m --summary consumer.json --metrics-port 9100
java -jar graal-native-sdk-nettest-<version>-all.jar NetTestApi --help
```

The all-in-one jar holds the other QD tools as well (`Help contents` lists them), so QD NetTest runs from it too.

## Command line

```text
NetTestApi p|c <address> -S <symbols> [-C <n>] [-s <period>] [-n <name>] [-c stream|ticker] [--event Trade|TimeAndSale]
           [--role <role>] [--duration <time>] [--warmup <time>] [--summary <file>]
           [--metrics-port [<host>:]<port>] [-D<key>=<value>...]
           p only: [-r */<rate>] [--batch <n>] [--reuse]
```

The mode comes first; the options may come before or after `<address>`. The long options take `--option value` and
`--option=value`, and a repeated option takes its last value. The options have the meaning and the limits of the
specification:

| Option                   | Meaning                                                                                       |
|--------------------------|-----------------------------------------------------------------------------------------------|
| `<address>`              | `:port` listens (the mux connects to it), `host:port` connects to a listening peer           |
| `-S <total>@<file>`      | the first `<total>` symbols of an IPF file                                                    |
| `-S <total>`             | `<total>` distinct symbols generated by QD NetTest                                            |
| `-C <n>`                 | instances: endpoints `NetTest.1` ... `NetTest.<n>`; not above 1 with `:port`. On `p` each instance has a generator thread and publishes all the symbols; on `c` instance `i` subscribes to the symbols with the index `j` where `j % n == i - 1` |
| `-r */<rate>`            | `p` only: the total rate of all instances in records per second, with `k`, `M` or `G`, kept by one schedule of whole batches (see [Statistics](#statistics)); without it the generators run flat out |
| `-s <period>`            | the statistics period, default `10s` (`ms`, `s`, `m`)                                         |
| `-n <name>`              | the name in the statistics lines, default `NetTest`                                           |
| `-c <contract>`          | the contract that the consumer receives, `stream` or `ticker`, and through it the roles (below) |
| `--event`                | `Trade` (default) or `TimeAndSale`                                                            |
| `--batch <n>`            | `p` only: events per `publishEvents` call, default 100                                        |
| `--reuse`                | `p` only: republish the pre-built events; without it every batch is made of new event objects, as an application that creates its events would do |
| `--role <role>`          | the role of the endpoints instead of the one of `-c`: `PUBLISHER` or `STREAM_PUBLISHER` on `p`, `FEED` or `STREAM_FEED` on `c` |
| `--duration <time>`      | end the run after this time; Ctrl+C (SIGINT, SIGTERM) ends it at once, a second Ctrl+C halts the JVM |
| `--warmup <time>`        | the warm-up from the first grant (`p`) or the first received record (`c`): its intervals are marked `warmup` in the summary and left out of its totals; default 0 |
| `--summary <file>`       | write the [summary file](#the-summary-file) when the run ends; a path whose directory is missing or not writable exits with 2 at once |
| `--metrics-port [<host>:]<port>` | serve [`/metrics`](#metrics) on the host, default `127.0.0.1`; port 0 takes a free port. A port that cannot be bound exits with 1 before the first endpoint |
| `-D<key>=<value>`        | set a system property before the first endpoint, for example `-Dmonitoring.stat=10s`; `-Ddxscheme.nanoTime` also goes to the builder of every endpoint (see below) |
| `--help`                 | print the usage with the line `spec_version nettest/1` and exit with 0                        |

The roles, as the specification sets them:

| `-c`     | Role on `p`        | Role on `c`   | Note                                                                     |
|----------|--------------------|---------------|--------------------------------------------------------------------------|
| none     | `PUBLISHER`        | `STREAM_FEED` | PUBLISHER writes the ticker and the stream contracts                     |
| `stream` | `STREAM_PUBLISHER` | `STREAM_FEED` | the contract of the benchmark; a mux between the tools runs with `-c stream` |
| `ticker` | `PUBLISHER`        | `FEED`        | the consumer receives conflated Trade events; needs `--event Trade`     |

`--role` replaces the role of `-c` only when the consumer still receives the contract of `-c`: `p -c stream --role
PUBLISHER` is valid, `c -c stream --role FEED` is valid only with `--event TimeAndSale`, and `-c ticker` takes only
PUBLISHER and FEED. `-c history` is reserved.

Not taken: `--legacy` (the C tool's deprecated publishing call), the `-X` and `-XX:` options (JVM options: put them
before `-jar`, see [Differences from the C tool](#differences-from-the-c-tool)), `-w` and the QD NetTest syntax that
the specification does not have (`{len,max}` and `/r`, `/s` in `-S`, a bucket `;<time>` in `-r`). An invalid command
line exits with 2 and prints the text of the specification first, for example `NetTestApi: unknown flag --foo`.

Every published event carries the current time: `setTimeNanos()` and a 22-bit sequence per instance
(`setSequence()`), as the C tool fills `time_sequence` (Trade) or `index` (TimeAndSale) and `time_nano_part`.

Every endpoint is built with `dxscheme.nanoTime=true` on its builder, so the nanosecond part goes on the wire without
an option; `-Ddxscheme.nanoTime=false` (or the same JVM option before `-jar`) turns it off for a run against peers
without it. The nanosecond part reaches a consumer only when every hop has the property: a multiplexor needs
`-Ddxscheme.nanoTime=true` on its command line, and a STREAM_FEED consumer needs it on its own builder (the system
property reaches only PUBLISHER and FEED endpoints), which `NetTestApi c` has. A hop without it still passes the
events, with the nanosecond part 0.

## The consumer

Each instance of `NetTestApi c` subscribes to its slice of the symbols: the listener is added first, then the symbols,
and the endpoint connects last. In each call of the listener the tool reads the clock once (`Instant.now()`); the lag
of each event is that time minus the event's time with its nanosecond part, and a negative lag (a clock step or skew)
enters the sum with its sign.

The consumer stops with exit code 1 and a line on stderr:

- `no_data`: with open connections, no records for 30 s after a record, or for 60 s after the connection when no
  record came at all;
- `nano_missing`: the first 1000 received events all have the nanosecond part 0, so a hop of the path lacks
  `dxscheme.nanoTime`. With `-Ddxscheme.nanoTime=false` the check is off and the lag is computed with the nanosecond
  part 0.

Exit codes: 0 after `--duration`, Ctrl+C or `--help`, 2 for an invalid command line or a `--summary` path that cannot
be written, 1 for a failure at run time: a failed start (unreadable IPF file, a metrics port in use, failed endpoint,
a `:port` that does not start listening within 3 s, for example because it is in use), a failed publishing call,
`no_data`, `nano_missing` or a summary file that cannot be written at the end. Connecting is asynchronous: a
`host:port` without a listener is not an error, the tool runs and reports `connections 0` until a peer is there.

## Statistics

At each multiple of the period on the wall clock the tool prints a block of the specification and the runtime line to
stdout in one write:

```text
{*NetTestProducerSide-NetTest*} data 1,767,033 rps, lag 57 us, instances 1, connections 1
    NetTest.1 data 1,767,033 rps, lag 57 us
{*NetTestRuntime-NetTest*} heap 137 MB of 491 MB, gc 3 (19 ms), cpu 102%
{*NetTestConsumerSide-NetTest*} data 1,767,020 rps, lag 412 us, instances 1, connections 1
    NetTest.1 data 1,767,020 rps, lag 412 us
{*NetTestRuntime-NetTest*} heap 98 MB of 256 MB, gc 2 (6 ms), cpu 85%
```

With `--metrics-port` a line with the address of the metrics comes first, once the port is bound:
`{*NetTestMetrics-NetTest*} http://127.0.0.1:9100/metrics`.

- `data`: on `p` the events handed to `publishEvents`, on `c` the received events, per second of the interval's real
  length.
- `lag` on `p`: the time to fill a batch and publish it, weighted by its events; the wait for the schedule is not
  included.
- `lag` on `c`: the mean end-to-end lag of the interval in microseconds, from the nanosecond time of the events; it
  may be negative.
- `connections`: open connections of all instances' connectors.
- A line per instance follows the first line, also for one instance.

The first tick prints no block. When the run stops, a last block covers the time since the last tick, if it is at
least one second long. The summary file has an interval for every part of the run, printed or not: the part before the
first tick and a short last part too.

The runtime line shows the JVM, in the format of the C tool's runtime line of the isolate, so that one load can be
compared between the JVM and the Graal isolate:

- `heap`: the used and the committed heap now, in MB (MiB, rounded down).
- `gc`: the stop-the-world collections of the period and their total time, summed over the JVM's collectors. The
  concurrent cycles of G1 (`G1 Concurrent GC`), ZGC and Shenandoah (`... Cycles`) are not counted, so with ZGC and
  Shenandoah `gc` counts their pauses, and their concurrent work shows only in `cpu`.
- `cpu`: the CPU time of the whole process in the period as a share of the period's length, so it goes above 100% when
  several cores are busy. The `CPU` of QD's `{NetTest.1}` monitoring line is divided by the number of processors.

A value that the JVM does not give is `n/a`.

With `-r` all instances share one schedule of whole batches: batch `k`, counted over all instances from the first
grant `t0`, is due at `t0 + k * batch / rate`. A generator sleeps until its batch is due; behind the schedule it
catches up without a pause and never drops a batch. The schedule slip of a batch is its start minus the time it was
due, so a publisher that cannot keep the rate shows a growing slip in the summary and the metrics, while its `lag`
stays the time of the publishing call.

The events come from the xorshift64* pools of the specification, and the generated symbols are those of QD NetTest's
generator in the order of their first appearance, so `NetTestApi p` and the C tool publish the same payload.

## The summary file

With `--summary <file>` the tool writes the summary `nettest-summary/1` of the specification when the run ends, also
after `no_data`, `nano_missing`, a failed publishing call or Ctrl+C (`status` `stopped_by_signal`, exit code 0). It
writes `<file>.tmp` first and renames it, so a reader never sees a part of it. The summary has the configuration of
the run, every interval with its phase (`warmup` or `measure`), the totals of the measured intervals, the percentiles
of the end-to-end lag on `c` (HdrHistogram, 1 ns to one hour, 3 significant digits), the publishing calls and the
schedule slip on `p`, the symbols seen on `c`, the runtime of the JVM and the statistics of every connector.

## Metrics

With `--metrics-port` the tool serves `GET /metrics` in the text format of Prometheus
(`text/plain; version=0.0.4; charset=utf-8`), one thread on the JDK's HTTP server, with the metrics of the
specification for the side: the records per instance, on `c` the histogram of the lag and the negative lags, on `p`
the time and the number of the publishing calls and, with `-r`, the schedule slip; the open connections, the bytes
and the records of the connectors, their round-trip time, subscription records and, on `c`, lag (the
`QDStats.SValue.IO_*` counters of the connectors), and the runtime of the JVM. The default host `127.0.0.1` keeps
them local; give `0.0.0.0:<port>` for a scrape from another host.

## Differences from the specification

None: the tool follows the whole [NetTest specification](../../docs/wrapper-guide/nettest.md).

## Differences from the C tool

- With `-r` the tool keeps the schedule of the specification and reports its slip; the C tool takes from a token
  bucket.
- The events are Java objects in a JVM with its JIT and GC, not in a Graal isolate: warm the run up before you read the
  numbers, and set the heap and the GC with JVM options: `java -Xmx2g -XX:+UseParallelGC -jar ... NetTestApi ...`.
- QD and MARS log their start (`Using QDS-...`, the multicast time synchronization), as every QD tool does.

## Running against QD NetTest

QD NetTest and this tool must use the same record and symbols: generated symbols are the same in both (QD's
generator), an IPF file works for any pair. A `PUBLISHER` endpoint feeds Trade to the ticker and the stream contracts,
and TimeAndSale to the stream and the history contracts. With the default `--event Trade`, QD NetTest as the consumer:

```shell
java -jar graal-native-sdk-nettest-<version>-all.jar NetTestApi p :6666 -S 50000 -r */1M -s 10s --duration 7m
java -Dcom.devexperts.qd.tools.NetTest.record=Trade -jar graal-native-sdk-nettest-<version>-all.jar NetTest c localhost:6666 -S 50000
```

For `--event TimeAndSale` drop the property (TimeAndSale is QD NetTest's default record) and give the consumer
`-c stream`: the default ticker consumer gets no TimeAndSale and reports `data 0 rps`. With
`--role STREAM_PUBLISHER` (or `-c stream`) every event goes to the stream contract only, so the consumer needs
`-c stream` for either event.

QD NetTest as the publisher, `NetTestApi c` as the consumer: QD's records carry no nanosecond part, so give the
consumer `-Ddxscheme.nanoTime=false`, or it stops with `nano_missing`:

```shell
java -Dcom.devexperts.qd.tools.NetTest.record=Trade -jar graal-native-sdk-nettest-<version>-all.jar NetTest p :6666 -S 50000 -r */1M -c stream
java -jar graal-native-sdk-nettest-<version>-all.jar NetTestApi c localhost:6666 -S 50000 -Ddxscheme.nanoTime=false
```

Against a mux, run the publisher with `:6666` and point the mux's distributor connector at it, and the consumer at
the mux's agent port.
